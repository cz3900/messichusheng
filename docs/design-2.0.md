# 2.0 设计：从"每帧判断"改成"估计一个受约束的组合对象"

> 这份文档描述的是尚未实现的架构。1.x 的现状见 [attribution.md](attribution.md)。

---

## 为什么 1.x 注定要一直打补丁

1.x 的每一帧都在问两个问题：**这格被拿走了吗？这槽有图标吗？** 然后用计数器去抖。

这个问题形式本身有三个后果，无论代码写得多好都躲不掉：

1. **每帧都要下硬判断** → 判错了就要能撤回 → 撤回逻辑本身会误触发 → 加防护（"已连续暗 12 帧不再撤"）→ 防护又挡住了正当的撤回。
2. **信息被丢掉**。一格在第 3 秒判成"看不清"，这个判断当场就作废了；哪怕第 20 秒面板上出现了决定性证据，也没有任何机制回头去改第 3 秒的结论。
3. **约束没被使用**。归属层 9 个步骤，本质都是在用启发式重新发现本来就已知的规则。

而真实要估计的东西，是**一个有强约束的组合对象**。这些约束是硬的、已知的、不要钱的：

| 约束 | 内容 |
|---|---|
| 顺序 | 一共 50 手，选人顺序固定（每轮反向），**高亮直接告诉我们现在轮到谁** |
| 单调 | 每一手正好拿走一件，拿走就不会回来 |
| 配额 | 每个人最后正好 1 个英雄 + 4 个技能 |
| 封闭 | 面板里只可能出现他自己拿到的东西 |
| 计数 | 任意时刻"已拿走的件数" = "已完成的手数" |

1.x **一个都没用上**。"手数不能多于棋盘暗格数 + 1"那条防御性上限，其实就是第 5 条约束的一个蹩脚的影子——把本来是等式的东西写成了一个容忍度为 1 的不等式补丁。

## 2.0 的问题形式

把状态拆成两个互相独立、各自干净的估计问题。

### 问题 A：每件东西什么时候被拿走

对每一件（60 格：48 技能 + 12 英雄卡），它的"被拿走"是一个**单调阶跃函数**——
在某个时刻之前没被拿走，之后一直被拿走。要估计的只有**那一个跳变点**。

这不是"每帧判断 + 去抖"，这是**变点检测**：给定这一格从锁池到现在的全部观测序列，
最可能的跳变时刻在哪里，以及跳没跳。

- 半透明浮窗飘过 → 那几帧的观测**似然低**，自然被序列里其它帧压过去，不需要"看不清"这个特例；
- 鼠标停在格子上 → 同理；
- 翻牌动画 → 同理。

**去抖计数器、闪烁标记、12 帧锁定、撤回逻辑，全部消失**——它们都是在用局部规则模拟"这一帧的证据不够强"。

再叠上第 5 条约束：任意时刻已跳变的格数 = 已完成手数。这是个等式，直接把
"凭空冒出 16 手"和"漏了一手"两类错误一起卡死，不需要任何容忍度参数。

### 问题 B：每件东西归谁

要估计的是一个函数 `owner: 件 → 座位 ∪ {没人要}`，约束是**每个座位正好 1 英雄 + 4 技能**。

证据来自面板：面板上出现一个和"割裂"匹配 0.95 的图标 → 这是"割裂归 R5"的强证据。
**注意用的是集合，不是槽位**——所以玩家拖动调换图标位置对这套方法完全无影响，
不需要 1.x 里"数图标总数而不是看第几个槽"那个专门的绕法。

把证据累加成一个矩阵 `W[件][座位]`，然后求：

```
最大化  Σ W[件][owner(件)]
约束    每个座位恰好 1 个英雄、4 个技能
        每件最多归一个座位
```

这是**带容量的二分图指派**，用最小费用流解。图小得可笑：

```
    源 ──(容量1)──→ 座位s的英雄口 ──→ 各英雄卡 ─┐
     └─(容量4)──→ 座位s的技能口 ──→ 各技能   ─┴→ 件 ──(容量1)──→ 汇
```

60 件 × 10 座位，求解一次几十微秒。可以每帧重算，不需要增量维护。

## 关键性质：**从不硬提交**

这是 2.0 和 1.x 最本质的区别。

2.0 里没有"记账"这个动作。证据只累加，不删除；每次查询都是拿**当前全部证据**重新求一次解。
于是：

- 第 20 秒的面板证据可以**直接改掉**第 3 秒的结论——不需要撤回逻辑，因为从来没有提交过；
- "连续几秒什么都看不见"之后，一旦重新看见，解会自己回到正轨（实测 1.x 在这种情况下会把技能**永久**分给错的人）；
- 某一帧的荒谬观测（浮窗、转场）只是一条弱证据，被其它几百帧压过去，不会造成任何持久后果。

1.x 需要 9 个步骤（A/B/C/C2/C3/D/D2/E/F）才能勉强模拟这个性质，而且模拟得并不好。

## 这一改会删掉什么

| 1.x 的机制 | 2.0 里怎么办 |
|---|---|
| 三态判定 + `darkRun`/`brightRun` 计数器 | 变点检测的似然项 |
| "闪烁"标记、连续 N 帧才认 | 同上，不需要特例 |
| "已连续暗 ≥12 帧不再撤回" | 不需要——从不硬提交 |
| 归属 9 步（A/B/C/C2/C3/D/D2/E/F） | 一个费用矩阵 + 一次最小费用流 |
| "手数 ≤ 棋盘暗格数 + 1" | 等式约束，不是不等式补丁 |
| 面板"图标数 − 已记账数"的绕法 | 天然用集合，拖动无影响 |
| 快通道落子并入局面（`fastPicks`） | 快通道就是一条弱证据，不需要特殊合并 |
| 重锁时手工拷贝 15 个字段 | 证据表本身就是全部状态 |

粗估能删掉 400~500 行规则代码，换成约 150 行的似然函数 + 一个现成的最小费用流。

**面板判空也一并改成自参照**：锁池那一刻面板必然全空（面板只在有人选完技能后才有图标），
把每个槽自己的空样子记下来，"有图标" = 和它自己的空样子不一样了。
这样 `slotFilled` 里的常数（均值 60、纹理 10）全部消失——和棋盘那边"跟它自己开局时比"的
原则统一。中途加入导致锁池时面板已经有图标的情况，那几个槽退回静态判据。

## 风险，以及怎么压

**风险 1：全局解可能"整体自洽但整体错"。**
实测过：证据弱的时候，指派会把两个技能对调（两边都说得通）。1.x 的局部规则不会犯这种错，
因为它根本不做全局优化。

**压法**：报告每件的**置信度**（最优解与"强制改判这一件"的次优解之间的差值）。
置信度低的不进入个人权重计算。而且"被拿走没有"（问题 A）和"归谁"（问题 B）是分开的，
前者才是引擎真正需要的，而它的观测质量高得多。

**风险 2：似然函数需要标定，标不好就是换一批魔法常数。**
这是真风险。**压法**：似然必须从真实数据标，不许拍脑袋。手上有 19 张真实截图 + 若干真机日志；
但日志里只有事件、没有观测。所以第一步要做的是——

**风险 3：这是归属层的重写，不是改动。**
**压法**：并行跑，不切换。`test/full_draft.js` 里已经有"普查版"这个并行位置，
2.0 先坐在那里，每次和 1.x 同时跑、同时报分；**在真机日志和模拟器上全部指标都不劣于 1.x 才切**。

## 落地顺序

**第 0 步：常驻真机基准。**（半天）
把 19 张真实截图固化成一张会自己报警的成绩单：池子读数逐格对照上一次的结果，
有变化就列出来让人过目。今天所有核对都是临时脚本量完就扔，改坏一次全靠运气发现——
没有这个，后面几步的"不劣于"根本无法验收。

**第 1 步：观测轨迹记录。**（半天，且**独立有价值**）
让工作线程把每帧的**观测**（每格的状态与置信度、面板内容、高亮在谁）压缩写进日志，
而不只是写事件。这样任何一版新代码都能拿真机的历史对局离线重放。
现在日志里只有结论，没有原始观测，所以没法回放——这是 1.x 最大的可测试性缺陷。
做完这一步，"在真机数据上对比两版"才成为可能。

**第 2 步：实现问题 A（变点检测）。** 先只替换"这格被拿走了吗"，归属层不动。
这一步就能删掉去抖计数器和撤回逻辑，而且能单独验证。

**第 3 步：实现问题 B（最小费用流指派）。** 在"普查版"位置并行跑。

**第 4 步：达标后切换，删掉 1.x 的规则链。**

第 0、1 步和 2.0 本身无关，就算 2.0 最后被否掉，它们也是纯赚。**先做这两步。**

## 诚实的边界

这套方案**不解决**识别层的问题。已经实测过：匹配配上贴准的框是 99.3%，
剩下的错格分数全 ≤ 0.48（系统自知没把握），而且试过的两条替代路线（全局单应矩阵、
梯度方向直方图）都被否掉了（见 [recognition.md](recognition.md)）。**匹配不是瓶颈。**

2.0 解决的是**状态估计**层：同样的观测质量下，把信息用足，并且不再需要靠加规则来堵漏。

它也不会"完美"。它会把当前这类 bug（撤回误触发、凭空手数、对调、永久错分）**整类消除**，
但会引入一类新的：全局解在证据不足时的整体性偏差。区别在于——那一类是**可测量、可报告置信度**的，
而现在这一类只能等测试者报上来，然后再加一条规则。
