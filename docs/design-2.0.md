# 2.0 设计：从"每帧判断"改成"估计一个受约束的组合对象"

> 状态：**问题 A / 问题 B 都已实现**（`v2.js`）。托盘菜单里可以把它切成驱动输出的内核，
> 但**默认仍是 1.x**。测试模式下两个内核并行跑、逐帧记录分歧。
> 1.x 的现状见 [attribution.md](attribution.md)；对比方法见 [testing.md](testing.md)。
>
> 线上开销实测:累计证据 0.87ms + 重解指派与置信度 7.58ms = **8.45ms/帧**，
> 而一次完整识别是 100~200ms —— 约 +5%。

---

## 为什么 1.x 注定要一直打补丁

1.x 的每一帧都在问两个问题：**这格被拿走了吗？这槽有图标吗？** 然后用计数器去抖。

这个问题形式本身有三个后果，无论代码写得多好都躲不掉：

1. **每帧都要下硬判断** → 判错了就要能撤回 → 撤回逻辑本身会误触发 → 加防护（"已连续暗 12 帧不再撤"）→ 防护又挡住了正当的撤回。
2. **信息被丢掉**。一格在第 3 秒判成"看不清"，这个判断当场就作废了；哪怕第 20 秒面板上出现了决定性证据，也没有任何机制回头去改第 3 秒的结论。
3. **约束没被使用**。归属层 9 个步骤，本质都是在用启发式重新发现本来就已知的规则。

版本记录本身就是这条链的证据：v1.13 的"已连续暗 ≥12 帧不再回撤"是**给回撤打的补丁**，
v1.15 的"手数 ≤ 暗格数 + 1"是**给面板误判打的补丁**，而 v1.16 才是那个误判的真根因。

而真实要估计的东西，是**一个有强约束的组合对象**。这些约束是硬的、已知的、不要钱的：

| 约束 | 内容 |
|---|---|
| 顺序 | 一共 50 手，选人顺序固定（每轮反向） |
| 单调 | 每一手正好拿走一件，拿走就不会回来 |
| 配额 | 每个人最后正好 1 个英雄 + 4 个技能 |
| 封闭 | 面板里只可能出现他自己拿到的东西 |
| 计数 | 任意时刻"已拿走的件数" = "已完成的手数" |

1.x **一个都没用上**。

> **关于第 5 条，一个必要的修正。** 初版设计文档写的是"高亮直接告诉我们现在轮到谁"，
> 把计数当成一条免费的硬约束。这是错的：`worker.js` 自己写着 *"顺序是死的，
> 比'当时高亮在谁那儿'可靠……实测有两个英雄被记到同一个 L1，就是这么来的"*，
> `pickCurrent` 还要靠三次峰值 + 连续两帧确认才敢换人。高亮是个**估计量**，不是观测。
> 把两个估计量之间的关系写成硬等式，一边错了会污染全局——比 1.x 那条只会夹住的不等式更危险。
>
> 等式的**另一种读法**是成立的，而且很强：把"已完成手数"换成**面板里有图标的槽数**。
> 22 张真机截图里可锁池的 17 张，面板槽数与棋盘"看着已被选走"的技能格数，**13 张精确相等**，
> 例外是 +10 / −1 / −1 / +1（那个 +10 的帧面板匹配中位只有 0.25，等式失败本身指向了真实缺陷）。
> 2.0 用的是这一版：约束取在**面板**那一侧，因为面板是持久的、不受棋盘那边遮挡的影响。

## 2.0 的问题形式

把状态拆成两个互相独立、各自干净的估计问题。

### 问题 A：每件东西什么时候被拿走

对每一件（60 个技能格 + 12 张英雄卡），"被拿走"是一个**单调阶跃函数**——
在某个时刻之前没被拿走，之后一直被拿走。要估计的只有**那一个跳变点**。

给定跳变点先验 τ ~ 几何分布(h)，和每帧的对数似然比

```
ℓ_t = log P(这一帧的样子 | 已拿走) − log P(这一帧的样子 | 没拿走)
```

"到现在为止已经被拿走"的后验几率有一行闭式递推：

```
U ← e^ℓ · (U + h) / (1 − h)          p = U / (1 + U)
```

**这一行就是问题 A 的全部状态。** 没有三态、没有 `darkRun`/`brightRun` 计数器、
没有闪烁标记、没有 12 帧锁定、没有撤回逻辑——它们都是在用局部规则模拟"这一帧的证据不够强"。
半透明浮窗飘过、鼠标停在格子上、翻牌动画，都只是让那几帧的 ℓ 接近 0，被序列里其它帧压过去。

> **一个必须记下来的坑。** 初版把先验写成"每一帧都是一个等权的候选跳变点"，
> 于是 `W ← e^ℓ·(W+1)`。这个写法有个致命性质：**就算每帧都毫无信息（ℓ = 0），
> 候选点个数也随帧数线性增长**——等得够久，任何一格都会被判成"已经被拿走"。
> 实测：被浮窗压暗 3 帧、每帧证据只有 0.1，后验照样冲到 0.89。
> 换成上面的风险率写法后，同样三帧只到 0.017。

### 似然从哪来

似然要是拍脑袋拍出来的，2.0 就只是"换一批魔法常数"。所以中心值全部从真机数据标：

**标签源必须独立。** 用"这件技能出现在某人面板里"当标签——面板和棋盘是两条互不相干的通道，
面板里只可能出现被选走的技能。在两张有真实落子的真机截图上得到 64 个正例，
用中位数 / MAD 稳健估计（抗住了标签源自身的漏标）：

| 特征 | 含义 | 已拿走 | 没拿走 |
|---|---|---|---|
| `r` | 本帧均值 / 锁池时均值 | 0.129 (MAD .033) | 0.988 (MAD .043) |
| `mr` | 本帧最亮一格 / 锁池时均值 | 0.217 (MAD .072) | 1.325 (MAD .234) |
| `ds` | 本帧饱和度 / 锁池时饱和度 | 0.319 (MAD .210) | 1.005 (MAD .020) |

三个特征在这批数据上**零重叠**。

**尺度不能用 MAD。** MAD 量的是干净变化，而我们需要的是"这个特征在没人落子的情况下还能动多远"
——也就是遮挡、悬停、反光、暗色原画。这一类**静态截图里一个样本都没有**：它们只存在于连续帧序列中。
所以尺度取 1.x 代码里记录下来的真机实测值（半透明说明框底下 r 只掉到 0.62~0.9、颜色还在；
被选走的格子 r = 0.08~0.28）。

这不是回避，而是对变点检测**恰好够用**：它要的不是"把难例分对"，
而是"难例给出 ℓ ≈ 0，被几百帧压过去"。两条尾巴有数据，中间要的就是不确定。
用柯西核而不是高斯，任何一帧的荒谬观测都只值有限的分数，不会一帧定生死。

### 共因：一手只选走一件

半透明说明框一帧能盖黑 30 格。每格独立累加的话，一帧就会判出 30 件被拿走。

1.x 用两条规则挡（"同一帧 ≥2 格新变黑 = 当遮挡，这几格要连续 5 次才认" + "手数 ≤ 暗格数 + 1"）。
2.0 把它写成模型：这一帧"刚开始变暗"的件数 k 越多，越可能是**一个共同原因**而不是同时落了好几手，
于是每件拿到的正证据按 1/k 打折。k=1（真落子）满分，k=30（浮窗）每件只值 1/30。
遮挡是短暂的、落子是永久的，所以已经连续暗了 4 帧以上的格子不再受这条约束。

再叠上面板那一侧的计数上限（被判定拿走的技能数 ≤ 面板有图标的槽数 + 余量，
余量是因为面板图标会晚 0~5 帧才画出来）。

实测：在真实轨迹上人为盖黑 30 / 50 格各 3 帧，**判定件数与不盖黑时完全相同**，
且整局收尾永远精确 50 件。

### 问题 B：每件东西归谁

要估计的是一个函数 `owner: 件 → 座位`，约束是**每个座位正好 1 英雄 + 4 技能**。
把面板证据累成矩阵 `W[件][座位]`，求最大总证据的带容量指派（最小费用流）。
72 件 × 10 座位，一次几十微秒，每帧重算都行。

**用的是集合，不是槽位**——某座位任意一个槽像某件技能，就算这件技能在这个座位的证据。
所以玩家拖动图标位置对这套方法完全无影响，1.x 里"数图标总数而不是看第几个槽"那个专门的绕法不需要存在。

> **证据必须按"已被拿走"的后验加权。** 一件技能在被人选走**之前**根本不可能出现在任何面板里，
> 那些帧的分数是纯噪声。不加权时实测一件技能的十个座位证据是 0.33/0.33/0.31/0.29——完全分不开；
> 按后验加权后立刻拉开。用后验（软的）而不是"等 p>0.5 再开始记"（硬的），是为了保住"从不硬提交"。

英雄卡在**面板上不存在**（面板只放技能），所以英雄只有两个信号：面板标题里的名字、选人顺序。
两者都进同一个费用矩阵：名字读到 ≥2 次给压倒性的分（与 1.x 的 F 步同口径），顺序给一个比技能重得多的权重。
名字本身还是"他已经选完了"的充分证据——所以棋盘上英雄卡整局没看出变暗时，2.0 照样能认定并归属。

---

## 关键性质：**从不硬提交**

2.0 里没有"记账"这个动作。证据只累加，不删除；每次查询都是拿**当前全部证据**重新求一次解。于是：

- 第 20 秒的面板证据可以**直接改掉**第 3 秒的结论——不需要撤回逻辑，因为从来没有提交过；
- "连续几秒什么都看不见"之后，一旦重新看见，解会自己回到正轨；
- 某一帧的荒谬观测只是一条弱证据，被其它几百帧压过去，不会造成任何持久后果。

## 实测：1.x ↔ 2.0，同一份轨迹

14 局（5 个普通种子 + 3 个额外种子 + 面板图标晚到 / 暗色原画 / 遮挡 / 连续致盲 / 英雄卡漏看 / 关掉名字信号），
共 1847 帧。两版跑在**完全相同的观测**上（见下"怎么做到的"）。

| | 1.x | 2.0 |
|---|---|---|
| 技能归属 | 550 / 560 | **555 / 560** |
| 英雄归属 | 140 / 140 | 140 / 140 |
| "认定被拿走"后又撤回 | 0 | **0** |
| 归属改判 | 0 | 90（其中 88 次发生在置信度 < 0.3 时） |
| 判定延迟（vs 1.x） | — | 中位 **+1 帧**，p90 +2 帧 |

**2.0 剩下的 5 个错全部是"两件技能在两个座位之间对调"**，正是设计上预料到的那一类
（全局解整体自洽但整体错）。而且**每一个都被置信度标了出来**：

| 置信度门槛 | 保留的正确归属 | 漏进来的错误 |
|---|---|---|
| ≥ 0.05 | 551 / 555 (99.3%) | 5 / 5 |
| ≥ 0.1 | 546 / 555 (98.4%) | 2 / 5 |
| ≥ 0.3 | 530 / 555 (95.5%) | **0 / 5** |

也就是说：拿 4.5% 的"标为不确定"换掉**全部**错误归属。1.x 完全没有这个输出。

### 三个必须说清楚的代价

**1. 2.0 慢一到两帧。** 变点检测的全部优势是"后面的帧能压过前面的帧"，
但建议必须在后面的帧到达**之前**发出去。落子后那 0.5~2 秒里，2.0 拿到的信息和 1.x 一模一样。
实测判定延迟中位 +1 帧、p90 +2 帧（单位是完整识别帧，约 1~2 秒一帧）。
**2.0 的收益集中在回溯纠正，不在实时决策。** 线上要不要切，得先看快通道那一路怎么接。

**2. 魔法常数没有消失，只是收敛成了少数几个。** 在线仍然需要"后验 > 0.5 就交给引擎当已拿走"这个门槛，
以及 `LMAX`（一帧最多值多少分）、`h`（风险率）、`DFREE`（连续暗几帧后不再受共因约束）、
`SLACK`（面板图标晚到的余量）。
但这是 4~5 个有出处、可标定的参数，替掉了 1.x 里散在九个步骤中的十几个门槛
（need=2/5/6、撤回=6、锁定=12、配对=0.2/0.45、补认=0.3/0.6/0.1、名字=0.40/0.50/0.10/0.15…）。
**是收口，不是消失。**

**3. 归属改判 90 次 vs 1.x 的 0 次。** 这是"从不硬提交"的可见代价。
但引擎真正消费的是"哪些东西被拿走了"，那一项 1847 帧里撤回 **0 次**；
90 次改判里 88 次发生在置信度还很低的时候。所以这笔代价是良性的——只要低置信度的不上屏、不进个人权重。

## 真机验收（2026-09-12，第一局带轨迹的真实对局）

合成测试**结构上**测不到真机的主要错误来源，所以上面那张表只能算"没被证伪"。
这一局是第一份真机证据：2560×1440，242 个完整识别帧，其中选技过程 228 帧。

| | 结果 |
|---|---|
| 选技全程有分歧的帧 | **10 / 228 = 4.4%**，每次都是单独 1 件、持续 1~3 帧 |
| 分歧的形状 | 全部是"只有 1.x 认为 X 被拿走"——就是那 1~2 帧的判定延迟 |
| **选满 50 手那一刻** | 技能归属 **40/40 一致**，英雄 **10/10 一致** |
| 2.0 的线上开销 | 均 **4.1 ms**，同期完整识别均 74 ms → **5.5%** |
| 整场错误/警告 | 0 |

**所以在真机上，2.0 整局跟 1.x 打平，唯一差别是慢一两帧。**
这既不能说明 2.0 赢，也不能说明它输——它说明的是：可以让它上场了，因为它不会更差。
要分出高下，需要一局 1.x 真的出错的对局。

### 这一局抓到的两个真问题（都已修）

**① 全局归一化有正反馈回路，选技结束时会雪崩。**
"跟这一帧的整体比"那条(见上)分母取的是"还没被拿走的格子"的亮度中位数。
选完时 60 格里 50 格真的被拿走，中位数本来就低；2.0 一旦错退一格，那格就进了分母把中位数拉得更黑，
于是更多格子看起来"没被拿走"——**退得越多退得越快**。真机上 50 件退到只剩 23 件。

修法有出处，不是调参：真机实测半透明说明框底下亮度只掉到 0.62~0.9，
所以"整体变暗"这个解释最多只能解释到 0.6，分母下限就钉在 0.6；
取样也从"p ≤ 0.3"收紧到"p ≤ 0.1"——只有**确信没被拿走**的格子才有资格当基准。
修后同一条轨迹：转场中稳住 50~51 件，只在棋盘真正消失的最后两帧掉到 44。
（同期 1.x 反向涨到 55 件——一局只有 50 手，它在凭空记。两边都是选技结束后的现象，不影响建议。）

**② "池外高分"这条判据太松，报的三次全是假阳性。**
测试模式第一次跑就报了三处"池子读错的铁证"。逐一查证：
一处全库前二是「冲击波 0.7212 / 弹幕冲击 0.7176」——领先只有 0.004，等于根本没认出来；
一处那个槽近乎全黑（选技结束转场）。而 v1.16 那次真正的铁证是 0.94 / 0.95 / 0.99。
补上最要紧的一条：**全库第一必须明显领先它自己的第二名**——认不出来的图标，前几名总是挤在一起。
同一条轨迹上假阳性从 7 帧次降到 0。

> 这两个都是**只有真机数据才能暴露**的问题：前者要一整局打完才触发，后者要真实的面板噪声。
> 合成测试跑了 14 局、1847 帧，一次都没碰到。

## 真机第二轮（2026-09-12 晚，两台机器 10 局 2705 帧）

第一局只是"没被证伪"。这一轮有了**两台机器打同几局**的配对轨迹，以及一个
**不需要人工标注的判据**：每个座位最后必须恰好 1 英雄 + 4 技能 = 5 件，这是游戏规则。
拿它直接给两个内核打分：

| | 1.x | 2.0（修前） | 2.0（修后） |
|---|---|---|---|
| **满 5 件的座位** | 85/100 | 82/100 | **86/100** |
| 手数（应为 50） | 456/500 | 451/500 | 451/500 |
| 两版有分歧的帧 | — | 22.5% | 25.5% |

**最该记住的一条：合成语料上 2.0 赢 5 件技能，真机上一开始却输 3 个座位。**
这正是本项目自己的教训——"合成测试结构上无法复现真机的主要错误来源"——现在轮到 2.0 头上。
真机轨迹第一天就推翻了合成结论。

### 这一轮修掉的 2.0 缺陷：费用流不肯分配零证据的件

x844 那局，2.0 让右1 **连英雄都没分到**，六件技能全是"无归属"。
根因是增广的停止条件写成了 `dist[T] < 0`——一件**完全没有面板证据**的东西整行都是 0，
那一步的收益恰好是 0，于是循环直接停，它永远留在原地。
每个座位的容量本来就是硬上限（1 英雄 + 4 技能），满了自然会停，不需要靠"收益为正"兜底。
改成只有"再增广会变差"才停之后：四局各涨 1，没有一局变差，82 → 86，反超 1.x。

> 这个缺陷合成测试一次都没碰到，因为模拟器里每件东西最终都会在面板上出现一次；
> 真机上"棋盘看见了、面板始终没画出来"是常事。

## 怎么做到的：观测轨迹（第 1 步，独立有价值）

要比较两版，必须让它们跑在**完全相同的观测**上。1.x 最大的可测试性缺陷是
**日志里只有结论、没有观测**——真机打过的对局没法回放，"新版本不劣于旧版本"根本无法验收。

做法是把追踪层真正从画面里读的东西收口成一个**可替换的观测源**（`recog.js` 的 `SRC`）：

| 观测 | 记什么 |
|---|---|
| 棋盘 60+12 格 | 亮度均值 / 最亮一格 / 饱和度（记**原始量**，不记三态判断） |
| 面板 40 个槽 | 均值 / 纹理（同理，"有没有图标"这条判据以后能换） |
| 面板某槽的图标匹配 | 对池子里每件技能的分数行（int16）+ 全库前二 |
| 面板标题英雄名 | 各候选的匹配分 |

线上 `SRC = null`，守卫直接落空，零开销、零行为改变（v1.17 与打完补丁的版本在 8 个种子上逐字相同）。

**验收标准是逐字相同**：同一局，读像素得出的归属和日志，必须和纯从轨迹回放（完全不碰像素）
得出的**一模一样**。11 种条件全部通过，观测缺口 0。
达到这条一共踩了四个坑，每一个都会让"回放"悄悄变成另一件事：

- 分数行用 int8（1/127 ≈ 0.008）→ 阈值边上翻判。换 int16。
- 记录时用**未量化**的原值、回放用量化值 → 两边看到的不是同一个数。量化一次，两边都用它。
- 懒加载补算的分数行没标成"这一帧新算的" → 落盘写成"接着上一行"，回放沿用了过期的行。
- 英雄名缓存没检查**是否覆盖本次全部候选** → 少一个候选，排序后的第一名就可能不一样。

代价：4.2 KB/帧（一局约 1 MB），**回放比线上快 600 倍**（1.3ms/帧 vs 100~200ms/帧）。
`worker.js` 已经在真机上默认开启记录，写在日志目录里，跟日志一起 7 天后清理。

## 诚实的边界

2.0 不会"完美"。它把当前这一整类 bug（撤回误触发、凭空手数、对调、永久错分）**整类消除**，
但引入了新的一类：证据不足时全局解的整体性偏差。
区别在于——新的那一类是**可测量、能报置信度**的（上面那张门槛表就是它的形状），
而现在这一类只能等测试者报上来，然后再加一条规则。
